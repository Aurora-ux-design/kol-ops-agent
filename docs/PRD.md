## 产品概述

### 1\.1 产品定位

达人运营智能 Agent 是一套面向品牌电商达人运营团队的 AI 决策辅助系统，覆盖达人运营全链路中四个核心决策环节——**选谁带货、怎么带货、赚不赚钱、投放值不值**——将运营从重复性手工劳动中解放，把精力集中在创意判断和关系维护上。

### 1\.2 一句话描述

> 输入一个商品，Agent 告诉你应该找哪个达人、用什么脚本卖、佣金给到多少不亏、投放有没有异常。
> 
> 

### 1\.3 目标用户

| 用户角色 | 使用场景 | 核心诉求 |
| --- | --- | --- |
| 达人运营（主要用户） | 日常选品、脚本分发、佣金谈判、投放盯盘 | 减少重复性工作，把精力留给达人关系和创意判断 |
| 运营主管/负责人 | 审核权重调整、预警规则配置、止损决策 | 全局可控、异常可追溯、决策有依据可复盘 |
| 投放/媒介 | 监控投产数据、处理异常告警 | 第一时间发现空耗和品控问题，减少无效消耗 |

管理规模：单个运营同时对接 50–100 个达人的中小型/成长期品牌电商团队，尚未具备自建数字化系统的能力和预算。

## 市场背景与用户痛点

### 2\.1 行业背景

直播电商达人撮合市场规模持续增长，但达人运营的数字化程度极低。大多数品牌方依赖"Excel \+ 微信群 \+ 人工经验"完成达人筛选、脚本分发、佣金谈判和投放监控。一个运营管理 50\-100 个达人时，大量时间消耗在重复性工作上，**真正的创意决策和达人关系维护反而被挤压**。

### 2\.2 核心痛点矩阵

| 决策环节 | 现状做法 | 核心痛点 | 隐性成本 |
| --- | --- | --- | --- |
| 选谁带货 | 凭经验 \+ 达人自荐 \+ Excel 记录历史合作 | 达人池越大越难凭记忆做最优匹配，容易依赖"熟人达人" | 错过更匹配的达人，GMV 天花板被经验局限 |
| 怎么带货 | 人工写脚本或让达人自由发挥 | 脚本与达人风格不匹配、跟不上热点节奏 | 完播率低、达人配合意愿下降 |
| 赚不赚钱 | 人工核算成本，Excel 拉公式 | 佣金谈判时无法快速给出保本线，容易谈亏 | 决策慢、错失窗口期，或谈判中让利过多 |
| 投放值不值 | 每天人工盯千川后台 \+ 群里问达人 | 无法及时发现空耗、也无法验证达人是否真的在讲本品 | 预算浪费、品牌方与达人间信任成本高 |

四个痛点共享同一个根因：**决策所需的信息分散在人的经验、Excel、聊天记录和多个后台里，没有被结构化和沉淀**，导致每次决策都要重新"从头想一遍"，无法复用过去的经验。

### 2\.3 为什么是现在

- **LLM 能力成熟**：语义理解 \+ 内容生成 \+ 结构化输出能力已经达到可商用的精度

- **API 生态完善**：巨量引擎 Marketing API、飞书开放平台、各 ERP 系统的接口标准化程度提高

- **行业效率洼地**：达人运营是电商最后一块没有被数字化的决策高地

## 引擎一：达人匹配引擎

### 4\.1 功能概述

根据商品信息，从达人池中智能筛选并排序最匹配的带货达人，输出排名、分数和匹配理由。支持商品→达人、达人→商品双向匹配。

### 4\.2 匹配流程

```Plain Text
输入商品
    │
    ▼
┌──────────────┐
│ Step 1: 粗排   │ ← ChromaDB 向量检索 Top 30
│ (语义相似度)   │   基于商品品类/人群/价格带 Embedding
└──────┬───────┘
       ▼
┌──────────────┐
│ Step 2: 精排   │ ← LLM 多维排序 Top 5
│ (多维打分)     │   维度：粉丝重合度/历史带货表现/
└──────┬───────┘        内容风格/佣金匹配/档期可用性
       ▼
┌──────────────┐
│ Step 3: 理由   │ ← LLM 为每个匹配输出可读理由
│ (解释性输出)   │   "该达人粉丝画像与商品目标人群重合度 82%"
└──────────────┘
```

### 4\.3 匹配维度与默认权重

| 维度 | 默认权重 | 数据来源 |
| --- | --- | --- |
| 粉丝画像重合度 | 25% | 达人粉丝画像 vs 商品目标人群标签，向量相似度 |
| 历史带货表现 | 25% | 该达人过去带同品类商品的 GMV/ROI/完播率 |
| 内容风格匹配 | 20% | 达人历史内容标签 vs 商品调性（如"性价比" vs "精致人设"） |
| 佣金匹配度 | 15% | 达人历史佣金率区间 vs 商品可承受佣金上限（来自损益引擎） |
| 档期可用性 | 15% | 达人近期排期是否冲突 |

> **运营可调控**：每个维度的权重可在后台调整。大促期可临时提高"历史带货表现"权重至 40%；新品首发期可提高"内容风格匹配"权重至 35%。
> 
> 

### 4\.4 达人→商品反向匹配

运营输入达人 → Agent 从商品库中推荐最适合该达人的 Top 5 商品，逻辑镜像匹配。

### 4\.5 匹配记录沉淀

每次匹配结果写入数据库，包含：匹配参数快照、采纳情况、后续实际 GMV/ROI，用于优化下一次匹配的权重分配。

## 引擎二：脚本生成引擎

### 5\.1 功能概述

为每一次匹配自动生成适配达人原生风格的带货脚本，支持三种内容形态 \+ 热点自动注入 \+ 运营可调控的创意参数。

### 5\.2 脚本生成流程

```Plain Text
输入：商品信息 + 达人画像 + 运营参数
    │
    ▼
┌──────────────────┐
│ 达人风格分析       │ ← 读取达人历史内容标签 + 语言风格特征
│ (向量+标签匹配)    │
└──────┬───────────┘
       ▼
┌──────────────────┐
│ 热点模式注入       │ ← 读取当前生效的热点词/BGM/Hook模板
│ (热点情报管道)     │
└──────┬───────────┘
       ▼
┌──────────────────┐
│ 模板骨架选择       │ ← Jinja2 模板：口播/剧情/测评
│ + LLM 内容填充     │
└──────┬───────────┘
       ▼
┌──────────────────┐
│ 合规检查           │ ← 禁用词过滤、广告法校验、品牌安全词库
└──────┬───────────┘
       ▼
输出：三版脚本 + 完播率预估 + 适用场景建议
```

### 5\.3 三种脚本形态

| 形态 | 适用场景 | 结构特点 |
| --- | --- | --- |
| 口播 | 达人擅长直接种草、商品卖点清晰 | 痛点引入 → 卖点罗列 → 促单话术，节奏快，依赖 Hook 抓开头 3 秒 |
| 剧情 | 商品有明确使用场景、目标人群情感驱动强 | 场景化短剧结构，商品作为"解决方案"自然植入 |
| 测评 | 商品有客观可验证的功能卖点（成分/效果对比） | 开箱 → 现场试用/对比 → 结论背书，强调真实感和可信度 |

三版脚本会同时生成，附带完播率预估分数供运营/达人选择，也可作为 A/B 测试的候选版本。

### 5\.4 热点情报管道

```Plain Text
数据源                      采集               提炼             审核        应用
──────                     ────              ────             ────        ────
蝉妈妈/飞瓜 ─┐
(垂类热门视频) │
              ├──→ 定时拉取 ──→ LLM 提炼 ──→ 运营审核台 ──→ 注入脚本
抖音热榜 ────┤    热点内容      热点模式      (采纳/拒绝/修改)   生成 Prompt
对标账号监控 ─┘
              │
运营手动补充 ─┘
```

**LLM 提炼维度**：热梗/热词、内容结构模式、BGM 趋势、Hook 模式、评论区洞察、周环比变化。

**热点生命周期追踪**：上升期 → 高峰期 → 衰退期 → 已过气。过气热梗自动标注"禁用"。

### 5\.5 运营调控参数

运营可在后台调整以下创意参数，无需改代码：

- **风格强度**：脚本贴合达人历史风格 vs 贴合品牌统一调性的权重比例
- **热点注入开关**：是否在生成时注入当前热点模板，以及热点权重高低
- **形态优先级**：针对特定品类/达人，可指定优先生成哪种脚本形态（如美妆类默认优先测评）
- **合规词库**：品牌安全词、行业禁用词可自行增删，无需走代码发布流程
- **脚本长度/时长**：适配不同平台（短视频 vs 直播口播）的时长要求

## 引擎三：损益计算引擎

### 6\.1 功能概述

支持自然语言输入，自动从 ERP 拉取成本数据，结合运营给的售价和达人佣金率，计算盈亏线、佣金上限、ROI 曲线，输出运营可决策的结构化结果。

### 6\.2 核心计算模型

```Plain Text
售价（P） ← 运营输入
    │
    ├── 总成本 = 采购成本 + 包装费 + 物流费 + 公摊 + 平台技术服务费 + 税费
    │           └── 以上各项从 ERP 自动拉取 ← 来自ERP
    │
    ├── 平台佣金 = P × 平台佣金率（如抖音 5%）
    │
    ├── 毛利 = P - 总成本 - 平台佣金
    │
    ├── 达人佣金 = P × 达人佣金率 ← 运营输入或自动计算
    │
    ├── 净利润 = 毛利 - 达人佣金
    │
    ├── ROI = P / (总成本 + 平台佣金 + 达人佣金)
    │
    └── 保本达人佣金率 = 毛利 / P （净利润归零的临界点）
```

### 6\.3 自然语言交互

运营用自然语言提问，Agent 完成"意图理解 → 结构化参数 → 调用确定性公式 → 结果人话化"的完整链路，例如：

- "这个商品卖 199，给达人 30% 佣金还能赚多少？" → 提取 {售价:199, 达人佣金率:30%} → 调用损益公式 → "净利润约 XX 元，ROI 为 X.X，还有 X 个百分点的佣金空间"
- "佣金给到多少还能保本？" → 提取当前商品成本结构 → 计算保本佣金率 → 直接返回百分比及说明
- "A 商品和 B 商品哪个利润率更高？" → 提取两个商品 → 分别计算 → 并列输出对比

每次查询都会先展示提取出的结构化参数供运营确认，避免因自然语言理解偏差导致算错的钱被直接使用。

### 6\.4 设计原则

**钱的计算不经过 LLM。** LLM 只负责意图理解（自然语言→结构化参数）\+ 结果解释（数字→人话）。算术部分全部走确定性 Python 公式，保证计算结果零误差。

### 6\.5 ERP 数据适配层

```Plain Text
ERPDataProvider（抽象基类）
    ├── CSVDataProvider       ← MVP 阶段：读取 CSV 导出的成本数据
    ├── DatabaseProvider      ← 第二阶段：直连 ERP 只读数据库
    └── APIProvider           ← 最终态：通过 REST API 实时查询
```

## 引擎四：投产审核引擎

### 7\.1 功能概述

对接巨量千川投放数据，自动检测投放异常、校验直播间是否在讲本品、支持可配置预警线与自动止损建议。支持自然语言查询。

### 7\.2 异常检测规则矩阵

| 规则 | 触发条件（默认阈值） | 严重度 |
| --- | --- | --- |
| ROI 异常 | 实时 ROI 低于该商品历史均值的 70% | 高 |
| 消耗异常 | 单计划 1 小时消耗超过日预算的 50% | 高 |
| CPM 异常 | CPM 高于同品类均值 1.5 倍 | 中 |
| 零转化空耗 | 消耗超过 200 元且 0 转化 | 高 |
| 未开播空耗 | 计划投放中但直播间未检测到开播信号 | 高 |
| 凌晨异常时段消耗 | AM 00:00–06:00 期间消耗超过日预算 20% | 中 |
| 点击率骤降 | 点击率低于该计划过去 7 日均值的 50% | 中 |

所有阈值均可由运营在后台调整。

### 7\.3 直播间品控校验（核心差异功能）

**背景**：千川后台只展示投放数据（消耗、展示、点击、ROI），不校验直播间实际在讲什么商品。存在达人拿着品牌投放预算在直播间推销竞品的情况。

**校验方案**：三重信号交叉验证

```Plain Text
信号 1: 直播间截帧         → 视觉识别：画面中是否出现本品
信号 2: 购物车/橱窗扫描     → 本品是否在橱窗中、排第几位
信号 3: 口播关键词匹配      → ASR 文字中是否提及本品/竞品关键词

交叉判定逻辑：

┌────────────────┬────────────┬────────────┬─────────────────┐
│ 截帧有本品      │ 橱窗有本品  │ 口播讲本品  │ 判定            │
├────────────────┼────────────┼────────────┼─────────────────┤
│ ✅             │ ✅         │ ✅         │ 🟢 正常          │
│ ✅             │ ✅         │ ❌         │ 🟢 正常(无口播)  │
│ ✅             │ ❌         │ ✅         │ 🟡 橱窗异常      │
│ ❌             │ ✅         │ ✅         │ 🟡 截帧未捕捉    │
│ ❌             │ ✅         │ ❌         │ 🟡 挂羊头嫌疑    │
│ ❌             │ ❌         │ ✅         │ 🟡 品在口播       │
│ ❌             │ ❌         │ ❌         │ 🔴 严重异常      │
└────────────────┴────────────┴────────────┴─────────────────┘

至少两路信号一致才出判定，单路信号不满足时标记"存疑"要求人工核查。
```

### 7\.4 预警 \& 止损配置

运营可在后台配置：

- 每条异常规则的**检测阈值**

- 异常触发后的**自动动作**（仅告警 / 告警\+建议暂停 / 告警\+自动暂停）

- **免打扰时段**（如 PM 22:00 \- AM 09:00 期间高危异常仍告警）

- **自动止损规则**：指定条件下自动调用千川 API 暂停计划（默认关闭，需运营手动开启）

- 日消耗 / 单计划日消耗**硬上限**

### 7\.5 自然语言查询

复用损益引擎的"意图理解 → 结构化参数 → 结果人话化"链路，面向投放数据场景，例如：

- "今天哪个达人的计划消耗最高但没转化？" → 结构化为空耗筛选条件 → 返回排序列表
- "A 达人最近三天 ROI 走势怎么样？" → 提取达人+时间范围 → 生成趋势描述 + 图表
- "现在有没有品控异常的直播间？" → 调用品控校验最新结果 → 汇总"存疑"与"异常"清单

## 运营调控中心

### 8\.1 统一审核台

四大引擎的运营调控集中在统一的 Streamlit 审核台中，按功能分为四个标签页：

| 标签页 | 功能 |
| --- | --- |
| 匹配参数 | 调整各维度权重、维护达人黑名单/加权名单 |
| 热点审核 | 对提炼出的热点模式做采纳/拒绝/修改，审核通过后才会进入脚本生成 |
| 损益参数 | 确认/修正 ERP 自动拉取的成本数据，避免脏数据影响计算结果 |
| 预警规则 | 配置各条异常规则的阈值、自动动作、免打扰时段 |

设计原则是**让运营始终拥有"最终拍板权"**——Agent 负责生成候选和建议，凡是涉及资金（止损、佣金）或对外内容（脚本、热点）的环节，默认都需要人工确认后才生效。

### 8\.2 飞书集成

飞书作为移动端告警和轻量审批入口，与 Streamlit 桌面操作台互补：

- **异常告警推送**：投产审核引擎检测到高严重度异常时，推送到指定飞书群/个人，包含异常类型、涉及计划、当前数据
- **待审核提醒**：热点/脚本/预警规则有新的待审核项时推送提醒，附操作台链接
- **轻量审批**：部分简单场景（如"是否暂停该计划"）支持直接在飞书卡片消息上一键操作，无需打开 Streamlit
- **敏感字段脱敏**：推送内容仅包含决策必需字段，达人联系方式、具体佣金金额等不通过飞书外发

## 非功能需求

### 9\.1 性能要求

| 场景 | 目标响应时间 |
| --- | --- |
| 达人匹配（粗排+精排+理由生成） | ≤ 10 秒 |
| 脚本生成（三形态并行） | ≤ 20 秒 |
| 损益自然语言查询 | ≤ 5 秒（确定性计算部分毫秒级，耗时主要在意图理解） |
| 投产异常检测（定时批处理） | 每 5 分钟一轮，覆盖当前所有在投计划 |
| 飞书告警送达延迟 | 异常检测到后 ≤ 1 分钟内推送 |

MVP 阶段以模拟数据/小规模真实数据验证功能正确性为主，性能指标作为后续版本的优化目标，不作为 V1.0 验收硬指标。

### 9\.2 准确性要求

准确性不是单一数字,不同引擎的"准确"含义不同,需要分别定义评估方法。

**9.2.1 达人匹配引擎**

GMV/ROI 是最终商业结果,但存在两个问题:一是结算周期长,达人排期、开播、结算往往需要数周,无法在推荐产生的当下判断匹配好坏;二是容易与达人体量本身混淆——百万粉达人带任何商品 GMV 通常都不差,不能说明匹配算法本身准。

因此采用分层指标,按时间顺序前置验证:

| 层级 | 指标 | 出现时间 | 衡量什么 |
| --- | --- | --- | --- |
| 即时 | 运营采纳率 | 推荐产生时 | 匹配理由是否让人信服 |
| 短期 | 达人实际配合率 | 数天内 | 达人是否愿意接这次匹配 |
| 中期(最终) | GMV/ROI 达标率 | 结算后 | 商业结果,权重占比最高(约 80%) |

为降低"达人体量掩盖匹配质量"的问题,GMV 评估采用相对值:对比该达人历史平均 GMV 与本次推荐商品的 GMV,而非只看绝对值。冷启动阶段(无历史 GMV 数据可参照)以采纳率和配合率作为主要评估依据,待数据积累后逐步提高 GMV 权重。

**9.2.2 脚本生成引擎**

避免直接大规模投流测试(样本量小、达人差异会混淆脚本差异、且真实投放成本高),采用三级筛选,先线下后线上:

1. **线下人工评分**:运营/达人对脚本打分;同时监测"达人拿到脚本后的修改幅度"作为质量代理指标——改动越大说明生成质量越差。
2. **同达人多版本对比**:同一达人在相似商品上试用不同版本脚本,控制"达人差异"这一混淆变量,而非跨达人比较。
3. **完播率作为先导指标**:完播率在直播结束后即可获得,比等待 ROI 数据快得多,用于短周期迭代;ROI/转化率作为最终验证指标。

**9.2.3 投产审核引擎(品控校验)**

三重信号交叉验证本身是一套检测系统,需要独立于业务效果单独建立评估基线:

1. 建立标注集:抽取历史直播片段,人工标注"是否实际讲本品"作为 ground truth。
2. 分别评估截帧识别、橱窗扫描、口播关键词匹配三路信号各自的误报率(未讲判定讲了)与漏报率(讲了判定未讲)。
3. 评估判定组合表整体表现:"存疑"占比过高说明单路信号可靠性不足、判定逻辑过于保守;漏判过多说明判定逻辑过于宽松。
4. 误判与漏判的代价不对称:误判可能触发自动暂停、伤害达人关系,代价高于漏判(仅浪费部分预算)。判定逻辑整体偏保守——即"自动止损默认关闭,需运营手动开启"这一设计的依据。待三路信号的历史准确率经过一段时间人工核查验证、达到可信阈值后,再逐步开放自动止损权限。

### 9\.3 数据安全

- API Key 存储在环境变量，不上传代码仓库

- 达人联系方式、佣金信息等敏感字段脱敏展示

- 飞书推送仅发送必要字段，不泄漏原始数据

## 成功指标

### 10\.1 北极星指标

**匹配采纳率**：运营采纳 Agent 推荐的达人并实际合作的比率。

### 10\.2 过程指标

过程指标是北极星指标(匹配采纳率)达成前的先导信号,用于在结果数据(GMV/ROI)回流之前快速判断系统是否在向好的方向迭代:

**达人匹配引擎**
- 运营采纳率(即时,推荐产生时可得)
- 达人实际配合率(短期,数天内可得)
- 推荐商品 GMV 相对该达人历史均值的提升幅度(中期,结算后可得,用于剥离达人体量本身的影响)

**脚本生成引擎**
- 脚本线下评分(人工/达人打分)
- 达人对生成脚本的修改幅度(代理指标,间接反映生成质量)
- 完播率(先导指标,直播结束即可得)
- ROI/转化率(最终验证指标,滞后但权威)

**投产审核引擎(品控校验)**
- 三路信号(截帧/橱窗/口播)各自的误报率与漏报率
- "存疑"判定占比(反映单路信号可靠性,占比过高说明信号不够可靠)
- 自动止损开启后的误判率(需持续低于阈值才维持开启状态)

| 外部数据 | CSV / ERP 导出、蝉妈妈/飞瓜、抖音热榜、巨量千川 API（后期） | MVP 阶段以 CSV 模拟，逐步替换为直连 |

### B\. 竞品对比

| 方案 | 优势 | 局限 |
| --- | --- | --- |
| Excel \+ 微信群（现状） | 零成本、灵活 | 无沉淀、无法规模化、依赖个人经验 |
| 通用达人 CRM / SCRM 工具 | 达人信息管理规范 | 只做信息记录，不做匹配/脚本/损益/审核决策 |
| 通用投放监控工具 | 投放数据可视化完善 | 不校验直播间实际内容，无法解决"品控"问题 |
| 本项目 | 四个决策环节串联成闭环，且在关键决策点（损益、品控）引入确定性验证而非纯依赖 LLM 判断 | MVP 阶段功能覆盖有限，需要真实数据持续迭代权重和阈值 |

### C\. 术语表

| 术语 | 含义 |
| --- | --- |
| GMV | Gross Merchandise Volume，商品交易总额 |
| ROI | Return on Investment，投入产出比，此处指 (转化金额/广告消耗) |
| CPM | Cost Per Mille，每千次曝光成本 |
| 千川 | 巨量千川，抖音生态官方投放工具 |
