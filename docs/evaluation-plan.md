# 达人匹配引擎 · 评测方案

> 状态：**设计阶段**。下文的数字阈值是初始设想，需要在跑出第一轮 baseline 后校准；示例样本为示意数据，不是真实结果。

## 1. 为什么需要评测

匹配引擎的输出没有唯一正确答案，同一个商品可能有很多合适的达人。如果只看最终 GMV，一是周期长，二是会被达人体量掩盖真实的匹配质量。所以需要一套**离线可重复跑**的评测，用来回答三件事：

1. 这一版比上一版好还是差（回归测试）
2. 错在哪里、占比多少（bad case 归类）
3. 能不能交给运营使用（上线门槛）

## 2. 评测对象：两阶段拆开评

| 阶段 | 做什么 | 评什么 |
|---|---|---|
| 粗排（向量召回） | 从达人库里召回候选 | 好达人有没有被漏掉 |
| 精排（LLM 排序 + 理由） | 对候选排序并写匹配理由 | 排序对不对、理由是否可信可用 |

拆开评的原因：召回漏掉的达人，精排再强也救不回来，两段的问题改法完全不同。

## 3. 评测集设计

### 3.1 构成
- **规模：** 第一版 40 个 SKU（够做出趋势，又能人工标得动），之后按 bad case 补充
- **覆盖（分层抽样，不是随机）：** 品类（食品 / 美妆 / 日用等）× 价格带（低 / 中 / 高）× 生命周期（新品 / 成熟）× 难度（常规 / 边界）
- **必须包含的边界样本：** 新品无历史数据、小众品类、价格极端、与现有达人池风格明显不匹配的商品、用户描述含糊的商品
- **冻结规则：** 评测集一旦标好就固定版本号（eval-v1），只增加不修改，保证不同版本的结果可比

### 3.2 每条样本的字段

| 字段 | 说明 |
|---|---|
| case_id | 样本编号 |
| sku_info | 商品信息（品类、价格、卖点、目标人群） |
| candidate_pool | 候选达人池快照（固定，保证可复现） |
| gold_strong | 专家认定"强推荐"的达人列表 |
| gold_ok | 专家认定"可接受"的达人列表 |
| gold_bad | 专家认定"明确不该推荐"的达人（含原因，如品类冲突、历史翻车） |
| difficulty | 常规 / 边界 |
| annotator_notes | 标注时的疑问与依据 |

关键设计：**标"可接受集合"而不是唯一答案**，并分三档，因为匹配本来就不唯一。

## 4. 评测指标

### 4.1 粗排
- **Recall@50：** 专家标注的强推荐达人，有多少出现在召回的 50 个里。**目标：不低于 90%**（初始设想）

### 4.2 精排（对照专家标注）
- **Hit@5：** 推荐的前 5 个里，至少有 1 个强推荐的样本占比
- **NDCG@5：** 强推荐排在前面得分更高，衡量排序质量
- **Bad@5（硬红线）：** 前 5 个里出现 gold_bad 的样本占比。**目标：低于 3%**，因为推荐明显错误的达人会直接损害运营信任

### 4.3 理由质量（人工打分，每条 1–3 分，抽样 30%）
| 维度 | 3 分 | 1 分 |
|---|---|---|
| 事实正确 | 引用的粉丝量、品类、历史数据都与数据库一致 | 出现编造或数据错误（幻觉） |
| 与结论相关 | 理由确实能支撑"为什么推荐这个达人" | 泛泛而谈，换个达人也能套用 |
| 可行动 | 运营能据此决定调整哪个权重 | 看完仍不知道怎么用 |

- **幻觉率：** 事实正确得 1 分的比例，**目标：低于 2%**

### 4.4 稳定性与公平性
- **一致性：** 同一输入跑 5 次，前 5 名的重合度（衡量输出波动）
- **分桶误差：** 按达人粉丝量分头部 / 腰部 / 尾部，分别看 Hit@5，检查是否系统性偏向头部达人（popularity bias）

### 4.5 业务指标（上线后，分层）
运营采纳率（即时）→ 达人配合率（短期）→ GMV / ROI 达标率（结算后）。离线指标与这三项的相关性，要在上线后回头验证，离线指标好不代表业务好。

## 5. 标注规范

### 5.1 三档定义
- **强推荐：** 品类与达人内容高度吻合，且受众与商品目标人群重合，近期有同类带货表现或明显匹配的人设
- **可接受：** 品类相关但不是主场，或受众部分重合，愿意尝试，风险可控
- **明确不该推荐：** 品类冲突（如母婴达人推酒类）、历史有品控 / 退货翻车、价格带与达人受众严重错位、近期有与品牌冲突的内容

### 5.2 边界处理
- 新品无历史数据：以达人内容与受众画像为主要依据，在 annotator_notes 注明"依据画像而非业绩"
- 达人近期数据缺失：不因缺失而降级，标注时说明
- 拿不准的样本：标"待议"，由两位标注者讨论后确定，不强行二选一

### 5.3 质量控制
- **双人独立标注**同一批样本，计算一致性（Cohen's kappa），**目标不低于 0.7**
- 分歧样本集中复议，复议结论回写到本规范，作为后续的判例
- 每轮标注结束抽检 10%，由第三人复核

## 6. Bad case 归类表

每个 bad case 都要归到一个原因，归类之后才知道改哪里：

| 编号 | 现象 | 可能根因 | 改法 | 严重度 |
|---|---|---|---|---|
| B1 | 强推荐达人没被召回 | 向量表示未覆盖该达人的内容特征；召回数 K 过小 | 补充达人标签、调整 embedding 输入、增大 K | 高 |
| B2 | 明显不匹配的达人进前 5 | 精排提示词缺少"不该推荐"的约束；权重设置不合理 | 加入负面规则、调整权重 | 高（红线） |
| B3 | 理由里编造数据 | LLM 没有绑定检索到的事实 | 理由只允许引用结构化字段；输出后做字段核对 | 高 |
| B4 | 理由正确但很泛 | 提示词没要求引用具体证据 | 要求每条理由至少引用 2 个具体字段 | 中 |
| B5 | 头部达人排名过高 | 粉丝量权重过大；训练数据偏向头部 | 降低体量权重；分桶评估后再调 | 中 |
| B6 | 新品推荐质量差 | 没有历史数据，只能靠画像 | 增加内容特征权重；冷启动单独评测 | 中 |
| B7 | 同输入多次结果差异大 | 温度参数过高；排序无稳定的打分依据 | 降低温度；先用确定性分数粗排再让 LLM 解释 | 中 |
| B8 | 输入描述含糊时乱推 | 没有澄清机制 | 信息不足时先向运营追问，而不是直接输出 | 低 |

## 7. 迭代流程

1. 每次改动（提示词、权重、检索、模型）后，在 **eval-v1** 上全量跑一遍
2. 与上一版对比指标，**任何红线指标变差即不合入**
3. 收集所有 bad case，按第 6 节归类，统计各类占比
4. **优先修占比最大、严重度最高的一类**，不凭感觉挑着改
5. 修完在同一评测集上复跑，确认该类下降且其他类没有变差
6. 每月把新发现的典型 bad case 补进评测集（eval-v2），并保持旧样本不变

## 8. 上线门槛（初始设想）

| 指标 | 门槛 |
|---|---|
| Recall@50 | 不低于 90% |
| Hit@5 | 高于现有人工 / 简单规则 baseline |
| Bad@5 | 低于 3% |
| 幻觉率 | 低于 2% |
| 标注一致性 kappa | 不低于 0.7 |

先用"简单规则 baseline"（如按品类 + 粉丝量排序）和现有人工选择作对比；如果引擎没有明显优于 baseline，结论本身也要如实记录。

## 9. 示例（示意数据）

**评测样本**
- case_id: C-007，SKU：低糖坚果礼盒，中价位，新品，目标人群为注重健康的上班族
- gold_strong: 达人 A（健康零食测评）、达人 B（职场轻食）
- gold_ok: 达人 C（泛美食）
- gold_bad: 达人 D（重口味零食，粉丝偏好与卖点冲突）

**Bad case 示例**
- 现象：前 5 名中出现达人 D，理由写"粉丝量大、零食品类相关"
- 归类：B2（明显不匹配进前 5）+ B5（体量权重过大）
- 根因判断：精排只看到"零食"这个大类，没有读到"低糖"卖点与达人 D 受众的冲突
- 改法：提示词加入"卖点与达人受众偏好冲突时不得推荐"；降低粉丝量权重；把 C-007 记入回归集
